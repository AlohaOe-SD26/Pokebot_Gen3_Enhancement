## The single most important miss: a Draw is mapped to "other", but the game treats a Draw as a defeat
- `outcome_bucket` sends anything that is not Won or Lost to "other" (`battle_log.py:411-415`). That includes Draw.
- The game whites out on a Draw. `IsPlayerDefeated` returns TRUE for `B_OUTCOME_DREW` (pret `src/battle_setup.c:994-1000`), and `CB2_EndTrainerBattle` whites out on it (`:1333`).
- **This already happens in real logs.** batch0927 has 5 Draws, and 3 of them are Tate & Liza: Mossdeep Gym map (14,0), Claydol L41 leading = `sParty_TateAndLiza1`, which is LEADER and a double battle. Each of the three is followed by `[STORY] WHITEOUT recovery`:
  - `P1-…-20260927-102251.log:22346`
  - `P1-…-20260927-102251.log:22987`
  - `P3-…-20260927-081746.log:16569`
- At (14,0) the `[MONEY] after` lines show 155 Lost, 3 Draw, 130 Won (the Won count includes gym trainers).
- **Effect on step 14:** in a batch with `[TRAINER]` telemetry these become KEY/other, so step 14's KEY won/(won+lost) silently drops real key defeats. Draws are a doubles event (both last mons faint, e.g. from recoil), and doubles are exactly where steps 13 and 14 act.
- **Gate coverage:** none. BA6 covers only Caught, no-end, and the Won fallback (`probe_itemprobes.py:611-616`).
- **Fix:** change `outcome_bucket` to map Draw to "lost", and add a row expecting "lost". The inverse mutant then has to redden that row. Until then, X1D only pins today's mapping.
- Separate finding about production, outside this item: `story_mode.py:2563,2574` counts defeats only on `outcome is BattleOutcome.Lost`, so a Draw-whiteout is not a defeat there either.

- In memory, a LEADER Won battle and a RIVAL Lost battle land in one row: `{('KEY','won'): 1, ('KEY','lost'): 1}`.

  - Add `key_group(classes)` and a per-group × outcome table that prints n and won/(won+lost).
  - Add outcomes to the boss probe, or remove the claim in its first line.
  - Pin it in the gate with T-ON (LEADER), Sidney (ELITE_FOUR) and M0's rival.

### SHOULD-FIX

**S1. Win rate is counted per attempt, so a few looping runs dominate it.**
- One run has 28 whiteouts after a battle on the Mossdeep Gym map (`P1-…-20260927-183007.log`); another has 27 (`…152227.log`).
- `first=` cannot pick out the first attempt: it reads the trainer-defeated flag, which stays unset (`first=True`) on every attempt until a win (`trainer_identity.py:179-186`).
- **Fix:** per key group, also report per (log, `opp`): first-attempt outcome, eventually won, and attempts to win.

**S2. The `[KEYBATTLE]` agreement check and the outcome tables are skipped when there are no item lines.**
- The NO DATA return (`probe_item_index_space.py:193-196`) comes before the `[KEYBATTLE]` report (`:236-240`).
- T-OFF1 shows it: "1 [KEYBATTLE] line(s)", then "NO DATA", exit 1, and no agreement verdict. A B-arm log that holds only refusals is exactly the case step 14 must check.
- Disagreements in WILD or UNCLASSIFIED battles are also dropped silently, because the offline value is None there (`:132-134`).
- **Fix:** run the outcome tables and the agreement check regardless of item data, and count "`[KEYBATTLE]` in a battle with no offline class" as a separate line.

**S3. "Wrong target" only means "the partner's HP rose".**
- `_AFTER_TARGET` and `_AFTER_PARTNER` are the only fields parsed (`battle_log.py:268-269`, `:291-296`). The emitter also prints `<item>=q0->q1 healed= same=` (`battle_action_selection.py:1227-1231`).

- Singles has no wrong-target signal at all: `✔ CONSUMED` only proves *some* Pokémon took the item.
- Arm B includes `POKEBOT_R27_DOUBLEITEMS=1` (per `04-HANDOFF`), so this column will be read in step 14.
- **Fix:** parse the item quantity and add a count of "bag dropped, target not raised, `same=1`". Reword the docstring's "the item applied".

**S4. Some boss-heal identities are ambiguous or false.**
