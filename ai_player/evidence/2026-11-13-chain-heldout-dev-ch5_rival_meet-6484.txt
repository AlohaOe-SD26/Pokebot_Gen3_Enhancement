LC.PURITY: on every leg that ran, the counting purity checks of live_step2.check_purity (L5.PURITY_GATE, L5.PURITY_CLEAN, L5.PURITY_PRESSES, L5.PURITY_FRAMES, L5.PURITY_BREACHES, L5.PURITY_PACKAGE) all PASS. L5.PURITY_ENDED is reported only.
LC.THIS_RUN: every leg that ran: L5.THIS_RUN (live_step5.check_after_is_this_run) PASSES. A leg whose launch died before playing a frame RAN (it was launched), so it fails LC.PURITY and LC.THIS_RUN and the batch, like any other leg: the reach tolerance does not cover it; its row and the evidence name it 'harness: the launch died before playing a frame', from the run's own exit facts (no exit by the AI, no frame counted, no line of the AI's log, no world file; a launch killed mid-play is not named).
LC.WORLD_SIZE: every leg that ran: its world.jsonl, measured before its deletion, is under 300000000 bytes (300 MB); if it grew between the first size and the deletion the larger is graded.
LC.CUSTODY: every registered chain's L1 ran, and every leg that ran started as above: L1 from --fresh with the chain's starter and no world memory or start state; each later leg from --state of the previous leg's end state, its start truth (frame, md5) equal to the previous leg's end truth, and an AI_PLAYER_WORLD file whose sha256 equals the previous leg's kept last line's; every leg's environment keys exactly the set above; every leg that ran names its registered job and shares no run folder or kept file, and no NOT RUN leg follows a continuing leg unexplained (as under LC.REACH). These checks read only the HARNESS's own records (the truth of one state file read twice, the sha256 of the one kept file, the keys of the environment run_chain builds and hands run_arm, whose clean_env also passes on the caller's variables that are not AI_PLAYER_*): on a later leg they catch a regression of the harness only, never anything the AI does.
LC.STARTER: every chain whose first leg left a party: its first Pokemon is the chain's registered starter, the player's own (OT).
LC.MEMORY (reads the AI's log, declared as B1 debt): every leg that ran said '[AI-WORLD] memory from ...': L1 from nothing (a new memory); each later leg from the last snapshot of its AI_PLAYER_WORLD file, with its maps, tiles learned, warp links, connections and map changes equal to the counts of the kept last line.
LC.FROZEN: the frozen-tree watch saw no change of the code under test from the batch's start to its verdict (a STOP.txt in --out, which the batch writes only when the tree moved, beside a record that says it held, fails it).
LC.LEFTOVER: no python process whose command line names ai-livechain- is left after the batch.
REPORTED (information, never counted): LC.PROGRESS (per chain the legs reached; per leg real frames of the budget, seconds of the wall), LC.MULTICHOICE (per leg the LINES of ai_player.log saying 'an unexpected multichoice', by form, and every 'an unexpected <kind>' line by kind: lines, not events), LC.OUTCOME (the AI's exit claim beside the game's proof), LC.ENDED (who ended each leg, the harness's own record), LC.OPTIONAL (the optional milestones' proofs at each chain's last leg), LC.WORLD (bytes per leg and chain; deletions; leftovers), LC.PROFILES (each chain's run folders are its legs', and no run folder of this batch's arms anywhere else), LC.MAIN_PROFILE (ai-step5-play's run folders and its state file unchanged).
VERDICT: PASS iff every GRADED check PASSES. Nothing is tuned to a grader (B1): a miss is reported, never re-run on new seeds. Every step that needs no chain (--out, the job files, the profile snapshots) runs before ledger.begin, so an --out that cannot be written is refused with the seeds unspent; a launch first claims --out by creating BATCH.claim.json there exclusively, so a second launch on the same --out is refused (R11) with the ledger untouched and removes only what it made itself. If the harness raises after ledger.begin, while the chains run (every running chain process is killed first) or while grading or writing the evidence, results.json or the ledger, the ledger entry is still FINISHED, as 'ERROR (harness: <type>: <message> while <stage>; no PASS or FAIL; the seeds are spent)' (the stage: the chains, grading, the evidence, results.json or the ledger), with whatever evidence could be written and the traceback, the way the disk guard's ABORT is recorded; a failed ledger write is retried with the computed verdict before it falls back to ERROR. While the entry is being finished a second Ctrl+C is ignored (a line says so first). The entry stays 'started' only if this orchestrator process is killed hard (its window closed, Ctrl+Break, a task kill), or if the ledger file cannot be written at all: the evidence and the output then say the entry is NOT finished and give the command that finishes it, which writes only this ERROR verdict. The offline re-grade (grade DIR) reads the batch's ledger entry and never reports a verdict better than it: an ABORTED or ERROR batch or entry is reported as such, a development batch is labelled development, and numbers that no ledger entry verifies never give a graded PASS.
