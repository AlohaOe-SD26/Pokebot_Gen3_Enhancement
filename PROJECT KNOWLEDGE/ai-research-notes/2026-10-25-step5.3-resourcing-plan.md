## (e) THE ACHIEVEMENT ASYMMETRY: ONE RULE

**The rule.** An ACHIEVEMENT check (a game read that an event HAPPENED in the run: a before/after change, or an end-state
flag, at a threshold of "at least one") is GRADED with no sweep control, provided its read has a known-answer FAULT test
both ways (a synthetic run in which the event did not happen reads FAIL, one in which it did reads PASS) and a
call-deleting mutant the suite catches. A BOUND check (a threshold on a quantity that both healthy and broken code produce:
a rate, a ratio, frames, a share, a count) needs a named control that fails it (spec line 102). WHY: an achievement's
null is the run where nothing happened, which a fault test builds directly; a bound's null is unknown without a control.

**What it changes:** L5.SHOPPED_GAME is GRADED (it was proposed REPORTED, row 19); L5.CAUGHT, L5.HEALED and L5.ITEMS stay
GRADED, now under a stated rule, and each must show its known-answer fault test and caught mutant (builder 2 checks; any
missing one is added). Nothing in rate_step5 changes: its R5 achievement checks (R5.CH1_REACHED, R5.CH2_WALLY) are shares
with bounds and keep their current form.
